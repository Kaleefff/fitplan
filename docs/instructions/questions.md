# Open questions

Agents add a line when a spec is silent or contradictory: `- [task id] key: question. Proposed default: ... (open)`. The task id is the task whose owner answers; the key is short and unique, and code TODOs cite `questions.md [task id] key`. A human answers by changing the spec files, then deletes the line. Answered questions are not kept here.


- [M-10, B-11] Should the user choose a preferred training intensity when generating a plan (light / standard / hard)? The request (`GenerateTrainingPlanRequest`) has no such field, so the app cannot offer it. Proposed default: an optional `intensity` field, default `standard` (today's behaviour, `algorithms.md` 4.7 unchanged); `light` = one set fewer per exercise (min 2) and rest +30 s; `hard` = one set more per exercise (max 6) and rest −15 s (min 30 s); the value is stored on `training_plan` and returned in `TrainingPlan`, so "generate again" keeps it; adaptation (section 6) is unchanged. Needs a contract PR (API and APP) and a migration (DATA). (open)
- [B-29] custom-exercise-generator: Does the training-plan generator (B-11, `algorithms.md` 4.6) use custom exercises (FR-P10)? Proposed default: no; a custom exercise reaches a plan only through a manual swap (4.9) until user-built plans exist. (open)
- [B-29] custom-exercise-injuries: Custom exercises have no `injury_type_excluded_exercise` rows, so rule 1 of `algorithms.md` 4.3 never excludes them. Proposed default: no extra rule; rules 2 and 3 (the affected group is the primary group, or a secondary group for a moderate or severe injury) apply in alternatives and eligibility as for library exercises. (open)

Proposed default: compliance is still computed as in section 7 (0 % when nothing was logged; null only without an active plan covering the window); the other metrics stay null and `key_lifts` is `[]`. - [B-25] `algorithms.md` 7 uses only the active plan, so the compliance of a past report period is null when the plan of that period has been archived since. Proposed default: each day of the period uses the plan in force that day: among the user's active and archived plans with `start_date` <= day <= `end_date`, the one with the latest `start_date` (archiving keeps the original `end_date`, so an archived plan overlaps its successor). Analytics windows ending today keep the active plan. (open)

- [B-20] manual-item-confidence: What `confidence` does an item added by hand (`POST /meals/recognitions/{id}/items`) get? It is not a model estimate, and `low_confidence` is derived from it. Proposed default: 1.0 (the user is certain), so `low_confidence` is false; `overall_confidence`, stored on the document at upload, is unchanged. (open)
- [B-20] review-duplicate: May the review list the same food twice (added again, or picked for another item)? Confirm then fails with 422 `duplicate` (`api-rules.md` "Logs"). Proposed default: adding or picking a food already listed is 422 `duplicate` right away, so the user changes the grams of the existing item instead. (open)
- [DB-12] seqscan-criterion: How is "no sequential scan on large tables" (`tasks.md` DB-12 Done) checked? At test and demo volume the planner prefers a Seq Scan on a small table even when an index fits, so a plain `EXPLAIN` says nothing about the indexes. Proposed default: "no sequential scan" is checked with `enable_seqscan = off` (`app/db/query_review.py`, `tests/db/test_query_plans.py`); an index scan in that pass proves an index fits the query. Two limits are reported, not asserted: (a) with sequential scans off, a query ordered by an indexed column (`ORDER BY id`, a merge join) may read a whole index instead of a missing one, so index scans without an `Index Cond` on a large table are listed as `[full]` for review; (b) the log tables' `UNIQUE (user_id, client_uuid)` (revision 0003) also serves user filters, so dropping `ix_workout_log_user_date` alone does not show as a Seq Scan. (open)
- [DB-13, B-27] body-metrics-uuid-rewrite: `BodyMetricsService.save` reuses the live row of a day that already has one and stores the request's `client_uuid` on it (`replace(..., client_uuid or day.client_uuid)`), so a POST with a new `client_uuid` rewrites the row's uuid. A pull then sends the row under the new uuid only; a device that holds it under the old uuid keeps that copy, and no tombstone for the old uuid is ever sent. Proposed default: the app keys body metrics by `measured_on` (one live row per day): a pulled live row replaces the local live row of that day, whatever its uuid. For B-27: a sync push create on a day that has a live row with another `client_uuid` is a `conflict` (with `server_copy`), not a rewrite. (open)
- [DB-13, B-27] full-download-tombstones: `api-rules.md` Sync says tombstones are included, but not whether a pull without a cursor (a first or full download) sends them too, though the client has nothing to delete. Proposed default: yes, a pull without a cursor sends tombstones like any other pull (`SqlSyncStore.changes_since`, `data` null), so every page has one meaning and a client may reinstall with old local data. (open)
- [B-27, M-20] plans-offline: `api-rules.md` Sync lists "plans (read)" among the offline entities, while `SyncEntity` in the OpenAPI has only `workout`, `nutrition_log` and `body_metrics`. Proposed default: plans are not in the pull; the app caches `GET /training-plans/active` and `GET /diet-plans/active` for offline reading and refreshes them when online. (open)
- [B-27] pull-data-shape: The OpenAPI gives the pull's `changes[].data` only as `object`; the push's `SyncChange.data` is `WorkoutInput`, `NutritionLogInput` or `BodyMetricsInput`. Proposed default: the store returns the views of the GET endpoints (`WorkoutView`, `NutritionLogView`, `MetricsView`), and B-27 maps them to the Input shape of the same entity, so a pulled item can be pushed back unchanged. (open)
- [B-27, M-20] cursor-goes-back: The last page's cursor is the database's `now() - 60 s` (`api-rules.md` Sync), which may be earlier than the cursor the client sent (after a `has_more` page ending in the last minute, or a cursor from the future). Proposed default: by design: the client always stores `next_cursor` as given and applies the repeated changes idempotently by `client_uuid` and `updated_at`. (open)
