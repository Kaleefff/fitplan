# Open questions

Agents add a line when a spec is silent or contradictory: `- [task id] question. Proposed default: ... (open)`. A human answers by changing the spec files, then deletes the line. Answered questions are not kept here.

All questions up to 19 Oct 2026 (including B-01, D-04 and D-03 of that day) are answered in `algorithms.md`, `api-rules.md`, `decisions.md` (D17–D23) and `tasks.md` (DB-01).
- [B-16] Section 6 progression is `planned_weight + step`, but a weighted exercise can still have `planned_weight` NULL after a workout with only 0 kg sets (no baseline). Proposed default: no progression for it until a set with weight > 0 sets the baseline. (open)
- [DB-01] `client_uuid` is unique across all users (tasks.md DB-01 item 13), so a create from user B that repeats user A's UUID can neither be stored nor answered with A's row, and api-rules.md does not say what B gets. Proposed default: unique per user, `UNIQUE (user_id, client_uuid)` on `workout_log`, `nutrition_log` and `body_metrics`, as migration 0002. (open)
- [D-03] `GET /notifications` (B-14): api-rules.md does not say which rows are listed or in which order; the `notification` table is also the push queue, so it holds rows scheduled in the future. Proposed default: rows with `scheduled_at <= now`, dismissed ones included, newest `scheduled_at` first, then id; paginated with `limit`/`offset`; no dismiss endpoint until a requirement asks for one. (open)
- [D-03] `DELETE /devices/push-token` (stretch S-03): the answer for a token that is not registered, or is registered for another user, is not specified. Proposed default: 204 and nothing changes (idempotent logout; another user's token is never touched and its existence is not revealed). (open)
- [B-03] Email case is not specified: `app_user.email` is unique as written and email-validator lowercases only the domain, so `Ann@example.com` and `ann@example.com` are two accounts and login is case-sensitive in the local part. Proposed default: lowercase the whole address on register, login and email change (one account per mailbox, as users expect). (open)
- [B-03] No DATA task covers the repositories the API needs outside libraries, logs and analytics (DB-06, DB-09, DB-10): `app_user`, `refresh_token`, `password_reset_token`, `oauth_identity` (B-02–B-05, B-07), `user_profile`, `injury`, `user_allergen`, `user_excluded_food` (B-06, B-10), training and diet plan persistence (B-11–B-13), `reminder`, `notification`, `device_push_token` (B-14), `progress_report` (B-25). D21 gives repositories to DATA. Proposed default: a new DATA task DB-14 "Account, profile and plan repositories" in stage 2, account and profile part first (blocks B-03, B-06, B-10), plans, schedule and reports in stage 3; until it is merged the API codes against a `Protocol` with in-memory fakes in `backend/tests/fakes.py`, as B-02 does. (open)
- [B-11] Section 4.5: with injuries a session can lose all its groups (6 days, weight loss, chest and shoulders skipped: Push has none left, triceps is not a main group). Proposed default: such a session trains every required group (Full Body) on its weekday. (open)
- [B-11] Section 4.6: when a session's extra slots outnumber the groups that have a second eligible exercise, the spec says only "second exercises". Proposed default: continue in the same priority with third exercises, never repeat an exercise in a session, and leave the session shorter when nothing is left. "Larger groups first" uses the same priority list. (open)
- [B-11] Section 4.6 sorts a group's eligible exercises by `is_compound DESC, difficulty_level DESC, id`, so equipment never counts: on the temporary seed a strength plan for a gym user has only 5 of 21 exercises that need the gym, the rest are bodyweight or home ones with lower ids. Proposed default: tie-break by equipment closest to the user's tier (`equipment DESC`) before `id`. Not implemented until answered. (open)
