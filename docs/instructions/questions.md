# Open questions

Agents add a line when a spec is silent or contradictory: `- [task id] key: question. Proposed default: ... (open)`. The task id is the task whose owner answers; the key is short and unique, and code TODOs cite `questions.md [task id] key`. A human answers by changing the spec files, then deletes the line. Answered questions are not kept here.


- [M-10, B-11] Should the user choose a preferred training intensity when generating a plan (light / standard / hard)? The request (`GenerateTrainingPlanRequest`) has no such field, so the app cannot offer it. Proposed default: an optional `intensity` field, default `standard` (today's behaviour, `algorithms.md` 4.7 unchanged); `light` = one set fewer per exercise (min 2) and rest +30 s; `hard` = one set more per exercise (max 6) and rest −15 s (min 30 s); the value is stored on `training_plan` and returned in `TrainingPlan`, so "generate again" keeps it; adaptation (section 6) is unchanged. Needs a contract PR (API and APP) and a migration (DATA). (open)
- [B-29] custom-exercise-generator: Does the training-plan generator (B-11, `algorithms.md` 4.6) use custom exercises (FR-P10)? Proposed default: no; a custom exercise reaches a plan only through a manual swap (4.9) until user-built plans exist. (open)
- [B-29] custom-exercise-injuries: Custom exercises have no `injury_type_excluded_exercise` rows, so rule 1 of `algorithms.md` 4.3 never excludes them. Proposed default: no extra rule; rules 2 and 3 (the affected group is the primary group, or a secondary group for a moderate or severe injury) apply in alternatives and eligibility as for library exercises. (open)
- [B-29] custom-exercise-delete: What happens on deleting a custom exercise that a session exercise (also as `original_exercise_id`), a logged workout (soft-deleted ones included) or a personal record still references? Proposed default: 409 `conflict`; an unused exercise is deleted for real. (open)
- [DB-16] custom-exercise-name: Are custom exercise names unique per user (case-insensitive), and may one equal a library name? Proposed default: unique per user on `lower(name)`; equal to a library name is allowed. (open)
- [B-29] custom-exercise-limit: Is there a limit of custom exercises per user? Proposed default: 200. (open)
- [B-29] custom-exercise-text: Are `description` and `instruction` optional for custom exercises? Proposed default: optional, stored as an empty string; schema unchanged; library rows keep the seed validation. (open)
- [B-29] custom-exercise-level: FR-P10 does not list `difficulty_level`, but the column is NOT NULL and a swap checks it against the plan's level (4.9 `above_level`). Proposed default: required on create, as for library exercises. (open)
- [B-29] custom-exercise-library-write: What does `PATCH` or `DELETE` of a library exercise answer? Proposed default: 404, as for another user's custom exercise (the repository finds no owned row). (open)
- [B-22] `algorithms.md` 10 step 1: which meal type must a single food fit for 5.2? Proposed default: at least one meal type of the active plan's slots (5.1), so a 3-meal plan never suggests a snack-only food. (open)
- [B-22] `algorithms.md` 10 step 4: when a remaining macro is 0 or negative, its ideal is not positive and the term divides by it. Proposed default: that macro is left out of the score. (open)
- [B-22] `algorithms.md` 10 step 4: tie-break between equal scores. Proposed default: planned meals first, then by meal or food id. (open)
- [B-22] `Suggestion` of a planned meal: what are `name`, `grams` and `nutrition`? Proposed default: `name` = "<Meal type>: <food names>" (for example "Lunch: Chicken breast, Rice"), `grams` = the sum of the item grams, `nutrition` = the meal's stored planned kcal and macros. A food with 0 kcal gets its largest portion (the limit of step 2). (open)
- [DB-10, B-23] `algorithms.md` 8 "A window without data gives null metrics": does this include compliance when an active plan covers the window but nothing was logged? `summary()` returns null for every metric, so a user who skipped every workout of the week sees no compliance instead of 0 %. Proposed default: compliance is still computed as in section 7 (0 % when nothing was logged; null only without an active plan covering the window); the other metrics stay null and `key_lifts` is `[]`. (open)
- [DB-10, B-23] FR-R5 minimum data: records may be dated up to tomorrow (`api-rules.md` "Dates"), so a record dated tomorrow counts toward the 7 distinct days while every window ends today. Proposed default: `record_days` counts only dates <= today in the user's time zone; the service passes today (`AnalyticsStore.record_days(user_id, today)`, a protocol change by API; the query by DATA). (open)
- [B-25] `algorithms.md` 7 uses only the active plan, so the compliance of a past report period is null when the plan of that period has been archived since. Proposed default: each day of the period uses the plan in force that day: among the user's active and archived plans with `start_date` <= day <= `end_date`, the one with the latest `start_date` (archiving keeps the original `end_date`, so an archived plan overlaps its successor). Analytics windows ending today keep the active plan. (open)
- [DB-10, B-23] `algorithms.md` 8 key lifts: (a) do incomplete sets count toward "most sets", the tie-break after most workouts? (b) when one of the top three exercises has no completed set with weight > 0 and 1–12 reps, it has no e1RM: is it skipped so the next exercise moves up? Proposed default: as implemented in `app/domain/analytics.py`: (a) every logged set counts (incomplete, 0 kg and over-12-rep sets included); (b) it is skipped and the next one takes its place; write both into `algorithms.md` 8. (open)
- [A-01] labels-source: Where does ai-service get the active recognition labels? Proposed default: the backend (B-19) sends them with every /predict call as the labels field and caches the list for 10 minutes; ai-service has no database access and holds only the Gemini key. (open)
- [A-01] labels-enum: D25 says the response schema restricts every label to the list, but Gemini (gemini-3.1-flash-lite) refuses an enum of the 504 seed labels with HTTP 400 ("too many states" / "too much branching"), even as a single enum with no other limits. Proposed default: the labels go in the prompt as a JSON array, the schema fixes only the answer's shape, and ai-service drops any item or alternative whose label is not in the list (matching trims and lower-cases, algorithms.md 11); D25's wording is updated. (open)
