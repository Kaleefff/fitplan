# MongoDB buffer for meal recognition

Based on thesis chapter 6.6 and decision D3.

## Purpose

MongoDB stores only temporary, unconfirmed results of meal photo recognition. The number and structure of recognized items is unknown in advance, so a flexible document fits better than relational tables. After the user confirms the result, the data is normalized and saved to PostgreSQL, and the document is deleted. Unconfirmed documents expire automatically.

## Lifecycle

1. User uploads a meal photo.
2. Backend sends it to the Vision API and matches recognized names to FoodItem records.
3. Result is saved as one document with `status: "pending"`.
4. User reviews the result in the app and corrects products or grams. Each correction updates the document.
5. On confirmation, the backend writes a NutritionLog row and its NutritionLog_has_FoodItem rows to PostgreSQL in one transaction, then deletes the document.
6. If the user never confirms, the TTL index deletes the document after `expiresAt`.

## Collection

Name: `meal_recognitions` (proposed, snake_case per D8)

| Field               | Type     | Description                                           |
| ------------------- | -------- | ----------------------------------------------------- |
| `_id`               | ObjectId | Generated by MongoDB                                  |
| `userId`            | int      | ID of the user in PostgreSQL                          |
| `status`            | string   | `pending`                                             |
| `mealType`          | string   | `breakfast`, `lunch`, `dinner`, `snack`               |
| `photoUrl`          | string   | Location of the uploaded photo                        |
| `overallConfidence` | double   | 0–1, confidence of the whole recognition              |
| `recognisedItems`   | array    | Recognized products, see below                        |
| `createdAt`         | date     | Creation time                                         |
| `expiresAt`         | date     | Deletion time used by the TTL index (createdAt + 6 h) |

Each element of `recognisedItems`:

| Field        | Type       | Description                                           |
| ------------ | ---------- | ----------------------------------------------------- |
| `name`       | string     | Product name                                          |
| `foodItemId` | int / null | Matched FoodItem ID in PostgreSQL; null if no match   |
| `grams`      | int        | Estimated or corrected portion                        |
| `confidence` | double     | 0–1, confidence for this item                         |
| `nutrition`  | object     | `kcal`, `protein`, `fat`, `carbs` for the given grams |
| `corrected`  | bool       | true if the user changed this item                    |

## Indexes

    // Deletes each document once its expiresAt time has passed
    db.meal_recognitions.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 })

    // Fast lookup of a user's pending recognitions
    db.meal_recognitions.createIndex({ userId: 1, status: 1 })

The TTL monitor runs about once a minute, so deletion is not instant. Expired documents may exist briefly, and the backend must ignore documents where `expiresAt` is in the past.

## Open questions

- Where photos are stored (local volume, S3-compatible storage) and whether they are deleted together with the document
- Whether a `failed` status is needed for Vision API errors, or errors are returned directly without saving
- Whether 6 hours is the right expiry time
